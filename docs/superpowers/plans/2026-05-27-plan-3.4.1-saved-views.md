# Plan 3.4.1 — Saved Views

Owner: Reese
Status: **Spec for review**
Predecessor: Plan 3.3 (Keyword Detail Page) + UI Phases A–E
Successor: Plan 3.4.2 (Watchlists)

## Goal

Let users save a named bundle of explorer filters, then re-apply that
bundle in one click from a "Saved Views" dropdown. After applying,
users can tinker with the filters on top of the saved view (changing
sort, week, leaf categories, etc.) without losing the original view.

This unblocks the workflow:
1. User builds a filter combination for their niche
   (e.g. category=Beauty + leafCategories=[Face Moisturizers, Serums]
   + rankMax=100000 + sort=avg_price_desc)
2. Saves it as "My beauty niche under 100k"
3. Returns next week, clicks the view in the dropdown — filters reload
4. Sees fresh week's data through that lens
5. Optionally changes sort to "Fewest avg reviews" without losing the view

## Out of scope (explicitly)

- **Sharing / org-level views** — every view is private to its owner
- **Per-view notifications** ("5 new keywords entered your view this
  week") — defer until later. A separate roadmap item already exists
  for a "new week's data is ready" digest, but that's per-user not
  per-view.
- **Watchlists** — Plan 3.4.2
- **In-watchlist filtering** — out of scope for both plans
- **Migration of legacy state** — no prior saved-search system exists

## URL contract

The explorer URL gains optional `?view=<uuid>`:

```
/explorer                                # no view, default filters
/explorer?category=Beauty&rankMax=50000  # filter-only URL (today's pattern, still works)
/explorer?view=abc123                    # saved view's filters fully apply
/explorer?view=abc123&rankMax=50000      # view applied, with rankMax override
```

Semantics:
- When `?view=<uuid>` is present and resolves to a view owned by the
  current user: the view's stored `filters` JSON is the BASELINE.
- Any other URL params are layered ON TOP of the baseline (overrides).
- The "Saved Views" dropdown shows the named view as selected.
- The Save button's behavior depends on whether overrides exist
  (see "Save flow" below).
- If `?view=<uuid>` is present but the view doesn't exist (deleted,
  or not owned by current user): silently ignore it — fall through to
  the URL params only. No 404, no error toast.

The current filter-only URL pattern continues to work unchanged.

## Schema (migration 0031)

```sql
CREATE TABLE saved_views (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name        text NOT NULL,
  filters     jsonb NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX saved_views_user_id_idx ON saved_views (user_id, created_at DESC);

-- Per-user uniqueness on name keeps the dropdown unambiguous and
-- supports "user already has a view called X" detection on save.
CREATE UNIQUE INDEX saved_views_user_name_uniq ON saved_views (user_id, name);
```

`filters` shape = a serialized `ExplorerFilters` object minus pagination
(`page`, `perPage` excluded — always reset to page 1 when applied).

5-view limit is enforced at the API layer (not in DB) so we can return
a clean error message; a hard CHECK constraint would be harder to
explain in the UI.

## Server-side data flow

`app/explorer/page.tsx`:
1. `parseExplorerFilters(searchParams)` (existing) returns filters
   parsed from URL params alone.
2. New: if `searchParams.view` is present, fetch the view from DB by
   id + user_id. If found, merge: `baseline = view.filters; result =
   { ...baseline, ...urlOnlyFilters }`. If not found, ignore.
3. Run the explorer query with the merged filters (existing code).
4. Also fetch the current user's saved views (5 max) and the active
   view (if any) to pass to `<FilterSidebar>` for the dropdown.

The merge needs to be careful about array filters (leafCategories,
severities, titleSlots). Rule: if the URL param for an array filter is
absent → use baseline. If present → fully replace (don't merge sets).

## API routes

All under `/api/explorer/saved-views`:

| Method | Path | Body | Response | Notes |
|---|---|---|---|---|
| GET | `/` | — | `{ views: SavedView[] }` | Returns up to 5 views for the user, sorted by created_at DESC |
| POST | `/` | `{ name, filters }` | `{ view: SavedView }` | Creates new view; 400 if user already has 5; 409 if name conflicts |
| PATCH | `/[id]` | `{ name?, filters? }` | `{ view: SavedView }` | Partial update (rename only, update-filters only, or both) |
| DELETE | `/[id]` | — | `{ ok: true }` | Hard delete |

All routes call `requireAuth()` first; ownership check on the row
(user_id matches session user) for PATCH / DELETE.

`SavedView` shape returned to the client:
```ts
interface SavedView {
  id: string;
  name: string;
  filters: ExplorerFilters;
  createdAt: string;
  updatedAt: string;
}
```

## UI flows

### Flow A — Save current view

1. User has filters set, clicks **"Save current view"** button (in the
   sidebar footer next to Reset).
2. If no view is currently applied (URL has no `?view=`):
   - Open the **NameViewModal** (lightweight modal with name input +
     Save / Cancel)
   - On Save: POST `/api/explorer/saved-views` with `{ name, filters }`
   - 5-view limit error: modal shows "You've reached the 5-view limit.
     Delete one to add a new view."
   - Name-conflict error: modal shows "You already have a view named
     'X'. Choose a different name or update the existing one."
   - On success: close modal, set `?view=<new id>` in URL, refresh
     sidebar dropdown
3. If a view IS currently applied and filters have been modified:
   - Open the **SaveOrUpdateDialog** with three options:
     - **Update '[currentName]'** → PATCH the existing view's filters
     - **Save as new…** → opens the NameViewModal flow above
     - **Cancel** → close dialog
4. If a view IS currently applied and filters HAVEN'T been modified:
   - The Save button is disabled with tooltip "No changes to save"

### Flow B — Apply a saved view

1. User opens the **Saved Views dropdown** (in the sidebar header,
   above the filter sections).
2. Clicks a view by name.
3. Page navigates to `/explorer?view=<id>` (replacing any current
   filter params).
4. Server hydrates filters from the view's stored JSON; explorer
   renders accordingly.
5. The dropdown now shows that view as the selected option.

### Flow C — Modify after applying

1. User has a view applied (URL has `?view=<id>`).
2. They change any filter in the sidebar.
3. On Apply: URL updates to `/explorer?view=<id>&<override params>`.
4. The dropdown still shows the view as selected, but the Save button
   becomes enabled (filter set differs from the saved filters).
5. Optional visual cue: an asterisk next to the view name in the
   dropdown chip — "My Beauty Niche\*" — indicating "modified".

### Flow D — Rename or delete from the dropdown

1. Each item in the dropdown has a small `⋮` icon at the right edge.
2. Clicking it opens a tiny popover with **Rename** and **Delete**
   options.
3. Rename → opens the NameViewModal pre-populated with the current
   name → PATCH `/api/explorer/saved-views/<id>` with `{ name }`.
4. Delete → confirm dialog ("Delete 'X'?") → DELETE the route. If
   the deleted view was the currently-applied one, also navigate to
   `/explorer` (drop the `?view=` param).

### Flow E — Reset clears the view

If the user clicks the existing **Reset filters** link in the
results header, the `?view=` param is dropped too — Reset means
"back to nothing applied", not "back to the saved view's defaults".

## Edge cases

| Case | Handling |
|---|---|
| User has 5 views, clicks Save | 400 from API, modal shows clear message |
| User saves a view with a name that already exists | 409 from API, modal shows message and offers to update existing |
| User applies a deleted view (stale URL link) | Silently ignore `?view=`, fall through to plain explorer |
| Stored filters reference a no-longer-existing leaf category | parseExplorerFilters already drops unknown values silently |
| User opens explorer with `?view=X` while logged out | Auth gate redirects to /sign-in (existing behavior) |
| User logged in as DIFFERENT user opens someone else's `?view=X` | Ignore the view (user_id mismatch) — show plain explorer |
| Schema drift: new filter added later, old views don't have it | `parseFilters` provides defaults for missing fields — no migration needed |
| Filters JSON corrupted somehow | Catch JSON.parse / schema validation error → log + treat as no view |
