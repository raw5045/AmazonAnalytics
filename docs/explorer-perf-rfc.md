# Explorer perf RFC — slow initial load on `/explorer`

## TL;DR

Users notice the keyword explorer feels slow on initial load. Per a
diagnostic that runs each variant 3× warm-cache plus `EXPLAIN
(ANALYZE, BUFFERS)`, the **default landing query (no filters except
the default severity, sort by current rank, page 1) takes ~2.7s
warm / ~9s cold** — a sort-to-disk over ~3.9M filtered kcs rows.

The page-1 SELECT, COUNT(*), and categories list already run in
parallel (`Promise.all`), pagination already only fetches 100 rows
per page, and the COUNT is already capped via a `LIMIT 10001`
bail-out subquery. The user's instinct was "are we loading all
pages?" — we're not. The slowness is in the **first** page's main
SELECT.

We want feedback on:

1. Is our **index strategy** the cleanest fix, given that kcs only
   ever holds rows for one `current_week_end_date`?
2. Is there a **query-shape change** (e.g. inject the current week
   predicate) that's better than adding indexes?
3. Are there **App Router-level perceived-perf** improvements
   (Suspense streaming, `loading.tsx` placement) we should layer on
   regardless?

---

## System context

- **Stack:** Next.js 16 (App Router) on Vercel + Neon Postgres.
- **`keyword_current_summary` (kcs)** — denormalized snapshot of "the
  most recent week per search term." Rebuilt via stage-and-swap after
  every weekly import (~30-100 min). Rows: ~3.9M active search terms.
- **`current_week_end_date`** — same value on every row of kcs (it's
  *the* current week). The kcs table is essentially a single-week
  snapshot.
- All explorer reads go through `kcs JOIN search_terms` for the
  display name.

## Existing indexes on kcs (relevant subset)

```
kcs_rank_idx           (current_week_end_date, current_rank)
kcs_severity_idx       (current_week_end_date, fake_volume_severity_current)
kcs_category_idx       (current_week_end_date, top_clicked_category_1_current)
kcs_title_match_idx    (current_week_end_date, keyword_title_match_count_current)
kcs_jump_4w_idx        (rank_4w_ago, current_rank)
kcs_imp1_idx           (improvement_1w)
kcs_imp4_idx           (improvement_4w)
… etc per improvement window …
PRIMARY KEY            (search_term_id)
```

Every "filter by week + something" composite index leads with
`current_week_end_date`. **The explorer query does NOT include a
`current_week_end_date` predicate**, so these composite indexes
can't be used for sorts in the absence of that leading-column
condition.

## The default explorer query

Generated by `buildExplorerQuery`. After `parseFilters` applies
defaults, the query (no URL params) is:

```sql
SELECT
  kcs.search_term_id,
  st.search_term_raw,
  kcs.current_rank,
  kcs.prior_week_rank AS prior_rank,
  kcs.improvement_1w  AS improvement,
  kcs.top_clicked_category_1_current,
  kcs.fake_volume_severity_current,
  kcs.keyword_title_match_count_current,
  kcs.keyword_in_title_1_current, kcs.keyword_in_title_2_current, kcs.keyword_in_title_3_current,
  kcs.keyword_title_match_count_loose_current,
  kcs.keyword_in_title_1_loose_current, kcs.keyword_in_title_2_loose_current, kcs.keyword_in_title_3_loose_current,
  kcs.top_clicked_product_1_asin_current,
  kcs.top_clicked_product_1_title_current,
  kcs.top_clicked_product_1_click_share_current,
  kcs.top_clicked_product_1_conversion_share_current
FROM keyword_current_summary kcs
JOIN search_terms st ON st.id = kcs.search_term_id
WHERE (kcs.fake_volume_severity_current IS NULL
       OR kcs.fake_volume_severity_current IN ('none','warning'))
ORDER BY kcs.current_rank ASC
LIMIT 100 OFFSET 0
```

Default filters:
- `severities = ['none', 'warning']` (the `'critical'` group is excluded)
- `matchMode = 'loose'`
- `sort = 'rank'` (current_rank ASC)
- `window = '1w'`
- `page = 1`, `perPage = 100`

Reading the plan:
- **Parallel Seq Scan on kcs** — reads all 3.9M rows; `Filter` keeps
  99.9% (severity defaults are permissive; only 3628 rows removed).
- **Sort by `current_rank`** — pushes ~850MB to disk across three
  workers (`external merge Disk: 279MB + 250MB + 319MB`).
- **Nested Loop + PK lookup on search_terms** — the join is fine; 100
  index hits, <1ms.
- **Limit 100** at the top — the planner has to fully sort the
  ~3.9M result set *before* it can pick the first 100, because no
  index supplies sorted output that the WHERE clause can ride.

So the 2.7s isn't pulling 3.9M rows over the network — only 100 rows
are returned. It's the sort-to-disk costing ~1.7s of write+read +
~1s for the seq scan.

The cold-cache version (9s) is the same plan paying for buffer reads
from Neon storage rather than the local page cache.

## Diagnosis

The bottleneck is **the default sort-by-rank with no index that
supplies sorted output**. Every existing kcs index leads with
`current_week_end_date`, which the query doesn't filter on, so the
planner falls back to seq scan + sort.

There's a subtle structural reason: **kcs only ever has one
`current_week_end_date` value** (it's the current week, refreshed
weekly). The composite indexes were designed under the assumption
that `current_week_end_date` is a meaningful filter axis — but in
practice it's a constant. The leading column adds zero selectivity.

## Candidate fixes

### A. Add a single-column rank index

```sql
CREATE INDEX kcs_current_rank_only_idx
  ON keyword_current_summary (current_rank);
```

Planner could use this for `ORDER BY current_rank ASC LIMIT 100`,
filter by severity inline (99.9% pass rate so basically reads first
100). Default landing should drop to <100ms warm.

Cost: ~3.9M tuple × 12-byte key = ~50MB index. Small.

### B. Add a partial index aligned with the default filter

```sql
CREATE INDEX kcs_current_rank_default_idx
  ON keyword_current_summary (current_rank)
  WHERE fake_volume_severity_current IS NULL
     OR fake_volume_severity_current = 'none'
     OR fake_volume_severity_current = 'warning';
```

Only contains rows matching the default-filter universe. Smaller
index (~99.9% of rows but slightly smaller per row). The planner
needs to recognize the filter implies the partial-index predicate —
usually does this for `IN`-list literal matches.

### C. Inject `current_week_end_date = ?` into the query

In `runQuery.ts`, fetch `MAX(current_week_end_date)` from kcs once
(or cache for a few minutes), then pass to `buildExplorerQuery` so
the existing `kcs_rank_idx (current_week_end_date, current_rank)`
becomes usable.

No new index, no schema change. But adds a query-planning round-trip
or a caching layer, and adds a parameter to every explorer query.

### D. Make kcs partitioned (or drop the leading column from existing indexes)

Heavy lift. Discounted unless someone makes a strong case.

### E. App-level: stream the page with React Suspense

Independent of any DB-side fix. Today the page server-renders
synchronously and waits for all three queries (`runExplorerQuery`,
`listCategories`) to resolve before any HTML is sent. With Suspense
boundaries:
- Header + filter sidebar can render immediately (categories cached)
- Results table streams in when ready
- Pagination footer streams in when COUNT(*) returns

Doesn't change query speed. Improves perceived latency materially —
the page feels alive immediately instead of staring at a loading bar.

### F. Keyset pagination for deep pages

Replace `OFFSET N LIMIT 100` with `WHERE current_rank > $last_rank
LIMIT 100`. Much faster for large N (constant time regardless of
page). Requires changing the pagination contract; users can't
"jump to page 50" directly anymore.

Worth it only if users actually go deep. Probably not the primary
need.

## Specific questions for review

1. **Indexing strategy** — Of A / B / C, which would you pick and
   why? (We're leaning A.)
2. **Should we drop the leading `current_week_end_date` from
   existing kcs indexes** given it's a constant? Or leave them and
   add new ones?
3. **Suspense streaming (E)** — worth doing regardless of the DB
   fix, or premature?
4. **Cold-start latency** (9s on the default landing first hit) —
   any practical mitigations beyond "warm the pool"?
5. **Anything else we should think about** — autovacuum cadence,
   stats, `random_page_cost`, work_mem on Neon, etc.?

## Constraints

- Pure Postgres SQL, no extensions.
- Neon Postgres (serverless, paid tier).
- Vercel serverless deploy; explorer page is a server component.
- Schema changes are OK but we'd rather add indexes than restructure
  partitioning.
- We can change the buildQuery shape if it materially helps.
